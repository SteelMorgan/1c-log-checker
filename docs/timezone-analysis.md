# Анализ работы с часовыми поясами: Grafana и ClickHouse

## Проблема

Пользователь ожидает:
- Событие в логе 1С: **14:59 MSK**
- Текущее время: **15:00 MSK**
- Фильтр Grafana "последние 7 дней" должен показывать это событие

## Документация

### Grafana `$__timeFilter` макрос

**Источник:** [Grafana Documentation - Macros](https://grafana.com/docs/grafana/latest/datasources/mssql/query-editor/#macros)

> **Важно:** Макросы времени (`$__timeFilter`, и т.д.) **всегда расширяются в UTC значения**. Если ваши временные метки не хранятся в UTC (обычно с типами `datetime`/`datetime2`), конвертируйте их в UTC в вашем SQL запросе используя `AT TIME ZONE … AT TIME ZONE 'UTC'` вместо передачи параметра часового пояса в макрос.

**Вывод:** `$__timeFilter(event_time)` всегда генерирует условие вида:
```sql
WHERE event_time >= '2025-11-17 12:00:00' AND event_time <= '2025-11-24 12:00:00'
```
где времена указаны в **UTC**.

### ClickHouse DateTime64

**Источник:** [ClickHouse Documentation - DateTime64](https://clickhouse.com/docs/en/sql-reference/data-types/datetime64)

1. **Хранение данных:**
   - Внутри хранится как количество тиков с эпохи (1970-01-01 00:00:00 UTC) как Int64
   - Часовой пояс **не хранится** в строках таблицы, а хранится в **метаданных колонки**

2. **Интерпретация без указания часового пояса:**
   > Если часовой пояс не указан, ClickHouse использует значение параметра `timezone` в настройках сервера или настройки операционной системы на момент запуска сервера ClickHouse.

3. **Текущая схема:**
   ```sql
   event_time DateTime64(6)  -- Без указания часового пояса
   ```
   Значит, используется часовой пояс сервера ClickHouse: **Europe/Moscow (MSK)**

## Текущая ситуация

### Конфигурация

1. **ClickHouse сервер:** `TZ=Europe/Moscow` (MSK, UTC+3)
2. **Grafana:** `timezone: "browser"` (использует часовой пояс браузера пользователя)
3. **Парсер:** `TZ=Europe/Moscow` (MSK)
4. **Таблица:** `event_time DateTime64(6)` без указания часового пояса

### Как это работает сейчас

**Пример:** Событие в логе 1С в **14:59 MSK**

1. **Парсинг:**
   - Парсер читает `20251124145900` из лога
   - Интерпретирует как MSK (из переменной `TZ`)
   - Конвертирует в UTC: `11:59:00 UTC`
   - Передает в ClickHouse как UTC `time.Time`

2. **Хранение в ClickHouse:**
   - ClickHouse сервер в MSK
   - Драйвер Go конвертирует UTC время в локальное время сервера (MSK)
   - Сохраняется как: `14:59:00` (интерпретируется как MSK)
   - Внутреннее значение: `11:59:00 UTC` (правильно!)

3. **Запрос из Grafana:**
   - Пользователь выбирает "последние 7 дней" в браузере (MSK)
   - Grafana конвертирует в UTC: `now-7d` в MSK → UTC
   - Макрос `$__timeFilter(event_time)` генерирует: `WHERE event_time >= '2025-11-17 12:00:00' AND event_time <= '2025-11-24 12:00:00'` (UTC)
   - ClickHouse сравнивает `event_time` (14:59:00 MSK = 11:59:00 UTC) с UTC временем из Grafana

4. **Проблема:**
   - ClickHouse интерпретирует `event_time` как MSK
   - Grafana передает UTC время
   - Сравнение происходит между MSK и UTC без конвертации!

## Решение

### Вариант 1: Хранить время в UTC (рекомендуется)

**Изменения:**

1. **ClickHouse сервер:** `TZ=UTC`
2. **Таблица:** `event_time DateTime64(6, 'UTC')` - явно указать UTC
3. **Парсер:** Конвертировать MSK → UTC перед сохранением

**Преимущества:**
- `$__timeFilter` работает напрямую (все в UTC)
- Нет проблем с конвертацией
- Стандартный подход

### Вариант 2: Использовать `toTimeZone()` в запросах

**Изменения в дашбордах:**

```sql
WHERE $__timeFilter(toTimeZone(event_time, 'UTC'))
```

**Преимущества:**
- Не требует изменения схемы
- Работает с текущей конфигурацией

**Недостатки:**
- Нужно обновить все дашборды
- Может быть медленнее (конвертация на лету)

### Вариант 3: Хранить время в MSK, но сравнивать правильно

**Изменения в дашбордах:**

```sql
WHERE toTimeZone(event_time, 'UTC') >= $__fromTime
  AND toTimeZone(event_time, 'UTC') <= $__toTime
```

Или использовать макросы с конвертацией:

```sql
WHERE event_time >= toDateTime($__fromTime, 'Europe/Moscow')
  AND event_time <= toDateTime($__toTime, 'Europe/Moscow')
```

## Рекомендация

**Использовать Вариант 1:** Хранить время в UTC.

Это стандартный подход для временных рядов и обеспечивает:
- Правильную работу с `$__timeFilter`
- Отсутствие проблем с часовыми поясами
- Совместимость с другими инструментами

## Доказательство проблемы

### Тест 1: Сравнение времени

```sql
SELECT 
  event_time,  -- 14:43:39 MSK (11:43:39 UTC)
  toDateTime('2025-11-24 12:00:00') as grafana_utc_time,  -- Grafana передает UTC
  (event_time >= toDateTime('2025-11-24 12:00:00')) as comparison_result
FROM logs.event_log
```

**Результат:**
- `event_time`: `2025-11-24 14:43:39` (MSK)
- `grafana_utc_time`: `2025-11-24 12:00:00` (интерпретируется как MSK!)
- `comparison_result`: `1` (true)

**Проблема:** ClickHouse интерпретирует строку `'2025-11-24 12:00:00'` как **локальное время сервера (MSK)**, а не UTC!

Это значит:
- Grafana передает: `'2025-11-24 12:00:00'` (ожидает UTC)
- ClickHouse интерпретирует: `12:00:00 MSK` = `09:00:00 UTC`
- Сравнение: `14:43:39 MSK >= 12:00:00 MSK` = `true` (но это неправильно!)

**Правильное сравнение должно быть:**
- `11:43:39 UTC >= 12:00:00 UTC` = `false` (событие старше часа)

### Тест 2: Правильная конвертация

```sql
SELECT 
  event_time,  -- 14:43:39 MSK
  toTimeZone(event_time, 'UTC') as utc_time,  -- 11:43:39 UTC
  toDateTime('2025-11-24 12:00:00', 'UTC') as grafana_utc_time,  -- Явно UTC
  (toTimeZone(event_time, 'UTC') >= toDateTime('2025-11-24 12:00:00', 'UTC')) as correct_comparison
FROM logs.event_log
```

**Результат:** `correct_comparison` = `false` (правильно!)

## Вывод

**Проблема подтверждена:** ClickHouse интерпретирует строковые значения времени из `$__timeFilter` как локальное время сервера (MSK), а не UTC, что приводит к неправильному сравнению.
