# 1c-log-checker

## Что это за проект

`1c-log-checker` — сервис и набор MCP-инструментов для работы с журналами 1С.

Основные задачи проекта:
- читать журнал регистрации 1С (`event_log`) и технологический журнал (`tech_log`);
- складывать данные в ClickHouse;
- давать доступ к данным и служебным операциям через MCP;
- помогать при диагностике проблем с логированием, правами, путями и настройкой техжурнала.

В текущем окружении проект используется и как парсер логов, и как MCP-сервер для отладки/проверки.

## Доступные инструменты для отладки и тестирования

### MCP: `1c-copilot-proxy`

Позволяет задать вопрос `1С:Напарник` — внешней LLM-модели со знанием платформы 1С.

Использовать, когда нужно:
- быстро сверить гипотезу по поведению платформы 1С;
- уточнить особенности журнала регистрации, техжурнала, кластера, `srvinfo`, `rac`;
- получить второе мнение по диагностике 1С-специфичных проблем.

### MCP: `1c-log-checker`

MCP-сервер на основе текущего проекта.

Использовать, когда нужно:
- проверить, что парсер и ClickHouse отдают ожидаемые данные;
- читать `event_log` и `tech_log` через MCP-инструменты проекта;
- смотреть текущую конфигурацию техжурнала;
- включать/выключать техжурнал и забирать диагностические данные.

### MCP: `1c-mcp`

Дополнительный MCP-прокси для работы с 1С, связанный с тестовой базой `drive`.

Использовать, когда нужно:
- выполнять операции через MCP, привязанные к базе `drive`;
- проверять состояние интеграции 1С вне `1c-log-checker`.

### SSH-доступ к серверу 1С

Каталог:

`/workspaces/work/repos/1C Framework/1c-log-checker/.ssh/onec-infra`

Содержит ключи для подключения к серверу 1С под пользователем `sandbox`.

Использовать, когда нужно:
- проверять файлы `srvinfo` и `1Cv8Log` на удалённой ВМ;
- смотреть процессы `ragent`, `rmngr`, `ras`, `rphost`;
- запускать `docker exec` в контейнере `onec-server`;
- проверять `rac`, права на файлы журналов и содержимое каталогов логов;
- править служебные скрипты/cron, связанные с правами и экспортом логов.

Примечание:
- доступ к Docker на ВМ обычно нужен через `sudo -n docker ...`;
- для доступа к файлам журнала и `srvinfo` часто тоже нужен `sudo -n`.

## Ограничения и безопасность

### Стенд `onec-infra`

Сервер `onec-infra` содержит только **копии** рабочих баз.

Разрешено:
- очищать и удалять файлы журналов, если это нужно для отладки или тестирования;
- пересоздавать журналы регистраций и техжурналы;
- очищать связанные с логами данные в ClickHouse, если пользователь этого просит.

### Критичное ограничение по базам

Сами базы удалять **нельзя ни при каких обстоятельствах без прямого подтверждения пользователя**.

Если агент считает, что для решения проблемы может понадобиться:
- удалить базу;
- пересоздать базу;
- очистить данные внутри базы;
- выполнить любые операции, затрагивающие саму ИБ, а не только её логи,

то агент обязан:
- не выполнять это самостоятельно;
- явно сообщить пользователю о риске;
- дождаться прямого подтверждения.

Это критичное ограничение.

### Строгий запрет на деструктивные действия по SSH без подтверждения

У агента есть доступ к SSH-ключам сервера 1С, поэтому любые деструктивные действия на удалённой ВМ запрещены без прямого подтверждения пользователя.

Под запретом без подтверждения:
- удаление файлов;
- массовая очистка каталогов;
- остановка сервисов;
- перезапуск сервисов;
- изменение прав доступа;
- изменение cron/systemd/docker-конфигурации;
- любые иные действия, которые меняют состояние сервера.

Без подтверждения разрешены только диагностические действия:
- чтение файлов;
- просмотр логов;
- проверка процессов;
- просмотр конфигурации;
- проверка сетевой доступности и содержимого каталогов.
Также разрешено удаление файлов логов, технологического журнала или журнала регистрации и связанных с ними файлов (не имеют ценности для пользователя, так как это девелопер-контур и логи ошибок нужны только "в моменте")

## Практические заметки

- Для проверки идентификаторов кластера и базы полезно использовать `rac` внутри контейнера `onec-server`.
- Если парсер видит `reg_1541` вместо GUID кластера или пустой `infobase_name`, сначала нужно проверить доступность `1CV8Clst.lst` и `1Cv8.lgf`.
- В текущем стенде `srvinfo` в контейнер парсера попадает через `sshfs`, поэтому права на файлы на удалённой ВМ критичны.
